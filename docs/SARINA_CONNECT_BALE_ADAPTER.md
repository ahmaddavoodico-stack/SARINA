# SARINA Connect — Bale bot and adapter specification

Status: planned adapter; not connected to a live Bale bot.

## Product decision

Use one official, centrally managed SARINA bot on Bale as the domestic Iran messaging entry point. One bot serves many private farmer conversations and routes each thread to the correct assigned specialist through SARINA Connect. Do not create one bot per farmer or per specialist. The sender remains the official SARINA bot; every specialist-authored reply must visibly name the verified human specialist it represents.

Bale is an optional channel selected by the farmer. It does not replace the SARINA in-app channel, Telegram, WhatsApp or direct human contact.

## Official API facts checked

Source: Bale official bot documentation, https://docs.bale.ai/ (reviewed 2026-11-20).

- Bot creation: contact Bale's official @botfather and create a bot; Bale issues a unique token.
- API base: https://tapi.bale.ai/bot<TOKEN>/METHOD_NAME over HTTPS.
- The API is based on Telegram Bot API with small changes; compatibility is a convenience, not a guarantee of complete feature parity.
- HTTP GET/POST are supported. JSON is supported except for file uploads; use multipart/form-data for uploads.
- Incoming updates: getUpdates long polling or HTTPS setWebhook.
- Bale documents retention of the latest 2,000 updates for 24 hours.
- Webhook ports documented by Bale: 443 and 88.
- Update objects may contain message, edited_message, callback_query or payment-related fields; consultation workflows should only process explicitly supported private-chat events.
- The reviewed official docs describe HTTPS webhook delivery but do not document a Telegram-equivalent signed secret header. Treat this as an unresolved security limitation; do not claim Bale's webhook has cryptographic provider signature verification.

## Adapter contract

Implement a provider-specific adapter behind the shared SARINA Connect interface:

- verifyIngress(request): validate HTTPS, unique high-entropy bot-specific path secret, method, content type, body size and JSON shape. Do not persist raw payloads.
- normalizeUpdate(payload): normalize update_id, chat.id, chat.type, sender.id, message_id, timestamp, text, supported media references and callback data into a provider-neutral envelope.
- resolveIdentity(chatId, senderId): resolve an existing consented provider route; never infer a SARINA user from a display name or phone number.
- sendText(route, message): call sendMessage and return provider message reference.
- sendAttachment(route, object): only for allowlisted/tested media types and after storage/security validation.
- acknowledgeCallback(callback): answer supported callback queries safely.
- mapError(response): map provider errors to retryable, permanent, throttled or user-unreachable categories without leaking raw provider payloads.

## Onboarding flow

1. Farmer chooses Bale in SARINA's channel settings.
2. SARINA shows the official bot identity and a link/open-bot instruction.
3. Farmer opens the bot and sends /start; the bot cannot initiate the first private conversation.
4. Bot presents a short, localized explanation and asks the farmer to link their SARINA account using a short-lived, single-use code generated by an authenticated SARINA session.
5. The farmer confirms channel consent for the selected consultation and its scope.
6. The backend binds the opaque Bale chat/user identifiers to the canonical SARINA user and consultation. Do not expose those identifiers to the specialist or other users.
7. Revocation in SARINA immediately disables the route and invalidates pending outbound jobs.

Never accept a user-supplied consultation ID as proof of access. Link codes must be random, single-use, short-lived, rate-limited, and bound to the authenticated user and intended channel.

## Message flow

- Inbound webhook is validated and acknowledged quickly; enqueue processing and deduplicate on provider + bot + update_id.
- Worker resolves the route and active consent, then writes one canonical message to expert_consultation_messages.
- Outbound messages are created from canonical messages through the transactional outbox; queue rows reference the canonical message only.
- Specialist identity is rendered in the outgoing text/template, while author identity is retained in the canonical record.
- If consent is revoked, route paused, mapping ambiguous or consultation closed, fail closed and do not deliver.
- No AI model is called for ordinary send/receive, attachment transfer or delivery receipts.

## Security and reliability

- Bot token belongs in a managed secret store and is never committed to Git or stored in client-readable Postgres.
- Use separate tokens for development/staging/production if separate bot identities are provisioned.
- Unique high-entropy webhook path per bot; rotate path/secret on suspected exposure. Because provider-side signature support is not documented, add request schema validation, strict size limits, replay/idempotency protection, rate limiting, monitoring and rapid acknowledgement. Do not rely only on source IP.
- Enforce private chat only for consultation messaging; ignore groups and channels in v1.
- Use update_id deduplication, bounded retries, exponential backoff, dead-letter queue and provider rate limits.
- Track update backlog and alert well before Bale's documented 24-hour update retention expires.
- Store media in SARINA object storage after validating MIME, size, ownership and malware status; do not assume provider file URLs are permanent.
- Do not use Bale payment/wallet APIs for SARINA billing in this phase.
- Normal Bale messaging must continue independently of AI credit balance and AI provider availability.

## Pilot scope

First pilot: /start, help, Persian/Arabic language choice, short-lived account-link code, per-consultation consent, plain text inbound/outbound, specialist identity disclosure, stop/revoke, webhook monitoring and delivery error handling.

Second phase after sandbox tests: photo/document/location/voice support, inline keyboards and callback actions. Enable each capability only after real-provider verification.

## Acceptance criteria

- One SARINA Bale bot serves multiple isolated private conversations.
- A farmer must start the bot before outbound delivery is enabled.
- Link codes cannot be replayed, guessed or used by another user.
- No message can be routed without an active route and explicit per-consultation consent.
- Replayed update_id creates no duplicate canonical message.
- Ambiguous provider identity fails closed.
- Specialist identity is clearly displayed in every relayed specialist reply.
- No token, chat identifier, raw webhook payload or secret path is exposed to clients or logs.
- Bale outage does not affect other providers or in-app messaging.
- Ordinary Bale communication never consumes AI credits.
- The bot can be disabled independently without deleting canonical consultation history.
